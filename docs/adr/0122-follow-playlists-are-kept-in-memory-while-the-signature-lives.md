# ADR-0122：清单正文在内存里复用，起播只回源一次母清单与一次子清单

- 状态：已采纳
- 日期：2026-10-25
- 相关：ADR-0121（按浏览器能力选编解码、分片交给浏览器缓存）、ADR-0120（起播钉最高档）、ADR-0119（母清单带全部档位、解析结果落盘复用）

## 背景

ADR-0121 之后同一条片子起播就是 4K、分片交给浏览器缓存，用户接着问「起播速度还能不能优化，
原站点起播特别快」。

实测（本机 headed Chrome、同一条 xHamster 条目、同一张 CDN、同一台机器）：

- **原站点起播快，一部分来自它先给低档。** 作品页第一次起播 4197 ms 时播的是 427×240，
  再开一次 3324 ms 时是 854×480：它自己的播放器先起低档再升，首帧只需几十 KB 的分片。
- **Peach 起播即最高档**（ADR-0120）：两次实测首帧分别为 2630 ms、3467 ms，落定在 3840×2160。
- **Peach 侧每次打开的两趟白等往返**。resource timing 显示一次起播依次是
  `/follow-stream` 532 / 501 ms、子清单 104–209 ms、再取首个分片；而 `curl` 复测同一份母清单
  冷连接 326 ms、热连接 86 ms，子清单每趟稳定 115 ms —— 两份清单的正文在签名有效期内一个
  字节都不变，却每次重开都回源取一遍。

## 决策

1. **母清单正文留在内存里。** `/follow-stream` 按（条目 id, 清单根地址）留 120 秒；
   命中就跳过上游那一趟。留的是改写前的正文，逐跳短键每次现生成——留着改写后的文本会把
   过期的键发出去。
2. **子清单正文同样留 120 秒。** `/follow-hls` 命中后照旧回 `no-store`：清单仍不交给浏览器
   留着（换签与解析失效的边界留在一处），省掉的只是 Peach 到上游那一趟。
3. **`forget(item_id)` 一并清掉这两类正文。** 上游拒收一份清单时，解析结果与清单正文一起作废，
   不留一份可能已经过期的地址。
4. **不做的两件事。** 不给 `/follow-stream` 加浏览器缓存（与「清单不落浏览器」一致）；
   不预留「预热子清单」：播放器拿到母清单后几十毫秒内就来要子清单，预热省不到时间。

## 后果

- 重开同一条、切一次清晰度、播放器重试取子清单，都不再回源；起播前那两趟往返只在签名
  刚换过或进程刚起来时出现。
- 首次打开仍要取一次母清单与一次子清单，因此仍比原站点慢一截：原站点首帧是 240p／480p，
  Peach 首帧是 4K。这个差距来自档位策略，不来自代理。
- 内存上限按「几屏反复点开」定：256 份清单正文；xHamster 4K 子清单一档约 48 KB。
- 回归：`tests/test_follow_xhamster.py` 覆盖正文的期限、容量淘汰与 `forget()`；
  `tests/test_fastapi_api.py` 覆盖「重开母清单与子清单各只回源一次」。

## 拒绝方案

- **把清单也交给浏览器缓存**：清单里是逐跳短键，键随解析换签而变，浏览器留久了会拿旧键
  去请求已经作废的分片；省一趟上游不值得引入这类失效。
- **后台预热子清单**：播放器解析完母清单立刻来要子清单，预热与它赛跑，实测省不到时间，
  只多一趟上游请求。
- **起播先给低档再升档（照抄原站点）**：与 ADR-0120「钉最高档、不降」冲突；是否改这一条
  要用户单独决定，不在本次改动范围内。
