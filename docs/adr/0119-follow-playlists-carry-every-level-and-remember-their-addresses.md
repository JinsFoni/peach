# ADR-0119：追更播放清单带全部档位，解析结果落盘复用

- 状态：已采纳（起播选档与窗口封顶两条由 ADR-0120 调整）
- 日期：2026-10-25
- 相关：ADR-0114（只有 HLS 的来源按清单改写播放）、ADR-0016（远端 mp4 默认 Range、HLS 显式开启）、ADR-0118（xHamster 追更来源）、ADR-0120（起播钉最高档）

## 背景

ADR-0114 让只有 HLS 的追更来源能播，但把来源给的各档收敛成一档：解析结果只留最高的那一
份清单，交给播放器的母清单里只有一条 `#EXT-X-STREAM-INF`。播放器因此没有可升降的档位，
网络一紧就只剩卡顿，用户能做的只有自己手动换档。实测（本机 Chrome，`/follow/item/45`
这类 Pornhub 条目）：

- 1080p 那档 `BANDWIDTH=5982759`，分片 10.24 秒、单块约 9.5MB。限速 5.6Mbps 播放时缓冲
  从 10.2 秒一路掉到 0.7 秒，五十秒里卡三次、累计 16.5 秒；同一条手动换到 480p 就不再卡。
- 拖动进度条要等一整块顶层分片落地：Pornhub 2.3 秒，xHamster 分片小（4 秒、2.4MB）好一些。
- 起播慢在解析：Pornhub 作品页把清单地址写成两种之一，带 `validto` 的那种能取回，只剩
  `?h=` 哈希的那种一律 410，一页里的各档同生同死，实测可用率约四成。串行重取最多六次，
  每次都要重新拉一份 1.5MB 的作品页（约 2.5 秒），起播实测 11.0–16.4 秒。

## 决策

1. **母清单带来源给出的全部档位。** xHamster 的母清单本身就写着各档，直接把它当播放地址；
   Pornhub 是「一档一份母清单」，由 `FollowMediaResolver.levels_master` 把其余各档并行取回，
   把每档自己那行 `#EXT-X-STREAM-INF`（带宽、分辨率、编解码原样）与它自己的子清单并成一份
   普通母清单。播放器因此拿到和原站点一样的自适应升降档；播放器点名要某一档时
   （`quality=`）仍换成那一档自己的清单，不做自适应。
2. **并好的母清单按清单周期留在内存里**（`PLAYLIST_TTL`），同一档连要几次不重复取；其余各档
   的母清单并行取，最坏多三次小请求。
3. **作品页并行取、各档按需探测。** 一轮并行取三次作品页（每次换一个没用过的参数绕开边缘
   缓存），最多两轮；一页里先验最高那一档，验不过再把其余各档并行验一遍。请求总数与串行
   六次相同，等待压到一轮。取回的页里若最高档已失效，只保留不比可播那档更高的档，免得
   播放器升上去再掉下来。
4. **已解析的地址写进状态目录**（`<state>/follow-playback/<item>.json`，权限 0600）。只存
   带明确到期时间（`validto`／`end`）的地址，剩余不足两分钟不写；从盘上读回时余量少于
   三十秒就宁可从作品页重解析。上游拒收一份清单时（签名到期就是 410）丢掉这一条的解析
   结果、重解析一次再取，不把「请再按一次播放」丢给用户。这是对 ADR-0114「不做自动续签」
   的调整：续签仍只发生在用户按下播放之后，只是同一次播放内多试一次。

## 后果

- 起播与拖动跟着档位走：实测 Pornhub 起播 11–16 秒降到 3.1 秒（冷缓存），限速 5.6Mbps
  播放不再中途卡顿；xHamster 从 240p 起播，4.5 秒升到 1080p、9 秒升到 4K。
- 自适应按客户端能测到的速率选档。分片是 Peach 边收边转的，客户端测到的就是上游实际给
  的速度，所以卡在上游时照样会降档。
- 起播与窗口封顶按 ADR-0120：播放器起播就钉最高档，小窗口不封顶，自适应只在观众于点名
  「自动」之后接管。
- 盘上那份是签名地址而不是数据本身：过期即失效，`forget` 与解析失败都会清掉它；条目删除
  时随 `follow_state_root` 下的其它状态一起清。
- 并档多出的几次请求只在播放时发生（每档一份小清单），不改变追更抓取的请求量。

## 拒绝方案

- **转码或重打包成统一码率的片子**：要跑 FFmpeg、吃 CPU 与磁盘，与「只读来源、不留中间产物」
  的边界不成比例。
- **按客户端速率在服务端选一档**：客户端速率要把分片先收下来才知道，等于把播放变成一次
  探测；而且换档就得换清单地址，播放器那边的键全失效。
- **给播放器喂一份伪造的 `BANDWIDTH`**：档位表与真实码率脱钩，自适应会做出更差的决定。
- **把整段片子缓存到磁盘换取拖动流畅**：这是「不留一批过期文件」的反面，且拖动本来就只需
  一块分片。
