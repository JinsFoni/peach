# ADR-0114：只有 HLS 的追更来源按清单改写播放

- 状态：已采纳
- 日期：2026-10-23
- 相关：ADR-0016（远端 MP4 默认 Range、HLS 显式开启）、ADR-0019（站点连接器）、ADR-0021、ADR-0091

## 背景

ADR-0016 把 HLS 定成显式的例外：远端媒体默认走标准 Range，HLS 只在用户开启时由
`stream-plan` 生成，理由是 HEVC-in-TS 会静默黑屏。STRM 资产另有自己的播放代理
（`strm_stream.py`），它按清单改写转发，不对外暴露上游地址。

新增的 `pornhub` 追更来源打破了「关注条目总能拿到一条渐进式媒体地址」这个前提：
它的作品页只给 HLS 清单，`format=mp4` 那条指向一个匿名取不到内容的接口。
如果沿用现有关注代理，这类来源只能在界面上显示「不可播」，点开就是一张空图。

## 决策

1. **关注来源的 HLS 走清单改写，不生成也不转码。** 播放器拿到的仍是 Peach 的地址：
   顶层清单由 `/follow-stream` 返回，清单里每一跳换成 `/follow-hls?id=&r=` 的短键，
   键到上游地址的映射只活在本机内存。改写复用 `preview_cache.rewrite_hls`（`m3u8`
   精确固定版本），与 STRM 路径同一份实现；不新增依赖。
2. **清单不进响应缓存，分片不进磁盘缓存。** 上游签名一小时过期，缓存只会攒下一批
   取不到的字节；解析结果本身在 `FollowMediaResolver` 里缓存两分钟，比签名短得多。
3. **解析推迟到按下播放。** 这类来源在账本里不存媒体地址（`media_url` 为空），
   只在播放时抓一次作品页。`playable` 的判据从「能代理 `media_url`」扩成
   「能代理 `media_url`，或者能按作品页地址在播放时解析」。判据两边同一份实现：
   界面说可播的，代理不会在白名单那一步拒收。
4. **页型由页面自己声明。** 同一站在 `/model/`、`/pornstar/`、`/users/` 三种路径下
   列的条数不同（实测同一演员 23 条与 49 条）。抓取按 `<link rel="canonical">` 认出
   真实页型并在进程内按 slug 记住；这是站点知识，不写账本，重启后重新发现一次。
5. **只读公开页。** 不带 Cookie、不登录、不求解任何质询、不碰付费或地区受限内容；
   凭据表里登记为 `none`。直接下载（`?download=1`）对这类条目明确拒绝，因为清单
   本身不是片子。
6. **写入边界不变。** 仍然只有 `save_asset(confirm=True)` 写真相，且只 INSERT 一条
   `location='online'` 的新 asset；播放、检查与解析都不写 ledger。

## 后果

- 关注页对这类来源可播、可选清晰度（清单里给几档就是几档），与 rule34video 的
  体验一致；上游地址（含签名）始终不出现在浏览器侧。
- 站点的清单地址会过期，播放中途超时需要重新打开；不做自动续签——续签要替用户
  重复请求站点，而这与「只在显式动作时联网」冲突。
- 分片不落盘，反复拖动会重复取流；这是拿带宽换「不留一批过期文件」。

## 拒绝方案

- **转码成渐进式 mp4**：要跑 FFmpeg、吃 CPU 与磁盘，且把一个只读来源变成有中间产物
  的管线，与本来源的边界不成比例。
- **把 m3u8 直接交给浏览器或系统播放器**：签名地址与主机就此外露，和整层的
  「上游地址不外露」冲突。
- **用浏览器驱动取页**：站点对标准桌面 UA 不设质询（ADR-0065 的适用前提不成立），
  起一个浏览器只会多一条故障路径。
- **按 `data-mediabook` 的预览片当正片**：那是两小时就失效的签名片段，不是作品本身。
