# ADR-0117：卡面封面立即取图，列表提前一屏接下一页

- 状态：已采纳
- 日期：2026-10-24
- 相关：ADR-0031（React + BoardUI）、ADR-0096（资料页在线视图）、`docs/MEDIA_CACHE.md`

## 背景

卡面封面格的底色是 `#000`（`.pic`、`[data-media-pic]`），格子里在等的那张图带 `loading="lazy"`。
浏览器把请求押到图快进视口才发，于是滚动时每一格都先黑一块，图到手才换成画面；在线卡片的封面
还要经 `/follow-image` 由服务端代取来源站，首次远端往返实测 245 ms 起（含 TLS 握手约 840 ms），
一屏四十张在 HTTP/1.1 的六条并发里排队，点亮过程能拖到一两秒。来源站给的是 320×180 的渐进式
JPEG（本机 `remote-media` 里四十八张封面全是 SOF2），字节到手后浏览器还要逐遍刷新。

懒加载省的是请求数，换来的是一屏黑：服务端封面命中本机缓存只要 3–5 ms，请求数在这台单人部署的
机器上不是瓶颈，等待才是。

## 决策

**一、卡面封面一律立即取图。** `coverImage`、`javArtwork`、`cardArtwork`、`mixFace` 与关注卡片的
`Thumb` 都写 `loading="eager"`，`eager` 这个开关从签名里去掉了：卡面的封面只有一种取法。图片按
文档顺序排队，浏览器自己按可见性给优先级，屏幕外的低优先级请求不会挤掉屏幕内的。

头像保持懒加载：索引页名册一次上千个头像，它们既不是卡面主角，也不撑起版面高度。`entityFaceImg`
的 `lazy` 参数留着给这些位置用。

**二、列表提前一屏接下一页。** `LoadMore` 的哨兵提前量是 1600px（约两个视口高）。卡片一插进文档
就取图，下一页的数据连同封面在用户滚到之前就位；新内容把哨兵推下去，取到「视口 + 提前量」填满
为止，不会一路追到列表末尾。翻页仍是同一枚哨兵、同一份失败重试，手动点它照旧等于提前取。

**三、封面缓存的口径不变。** `/follow-image` 命中本机 `remote-media` 的副本，响应头是
`Cache-Control: private, max-age=31536000`；浏览器拿到的始终是本机副本。预取只改变「什么时候读」，
不改变「读什么」：未读过的媒体不会在后台批量下载。

## 后果

首屏一次会发出一整屏的图片请求：目录页每页几十张，服务端同时最多六个生成任务（六连接上限），
本地封面命中时总计几十毫秒，缺封面时单个 ffmpeg 抽帧仍按文件加锁，不会互相踩。

进度条式的等待态（`.imgwait` 微光）按 180 ms 门槛出现在卡面上：`PENDING_IMAGES` 收
`[data-media-pic] > img`，插进页面时还没到手的封面把微光铺在格子上，到手后淡出。卡面底色是
`#000`，没有这层等待态，冷缓存下四十张一起取的几百毫秒里就是一整片黑（实测首屏四十张封面在
浏览器缓存命中时 244 ms 内全部就位，冷缓存时最后一张到 0.5–0.75 s 才到）。封面从缓存直出时
摸不到门槛，不会闪一下。

## 验收

- 宽 1440 的空白缓存下打开艺人页：四十张卡面图片随卡片一起发出请求，滚动到底不再触发新请求。
- 下一屏的卡片在进入视口前已经在文档里，其封面请求与卡片渲染同一帧发出。
- `frontend/test/card-art/markup.test.ts` 断言四种封面模板都是 `loading="eager"`；
  `frontend/test/react/follow-feed.test.tsx` 断言关注卡片封面立即取；`frontend/test/react/load-more.test.tsx`
  断言哨兵的提前量与「一进入就续页」。
